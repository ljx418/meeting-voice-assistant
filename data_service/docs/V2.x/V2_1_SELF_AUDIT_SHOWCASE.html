当前可审计能力

能力 当前状态 可用于审计的问题 主要风险
Repo Snapshot 可用 文件树、语言分布、重要路径、忽略策略、敏感文件跳过。 不是完整增量构建语义。
Public Surface Inventory 可用 HTTP / MCP / CLI 公开能力、三端对齐、legacy 与 target 差异。 动态注册和复杂前端调用仍可能需要人工复核。
Python Symbol Index 可用 模块、类、函数、方法、import、line range。 不做类型推断、运行时派发、完整调用图。
Evidence Trace 可用 capability 到 surface、symbol、file、line 的证据链。 低置信度和 unresolved 映射必须保留，不应被包装成成功。
DevWiki 可用 项目概览、架构、HTTP、MCP、CLI、存储、构建链路等可读页面。 不是 LLM 任意总结，必须依赖已有 artifacts 和 evidence。
Code Graph 可用 File / Module / Symbol / Surface / Capability / Evidence / DevWiki 关系。 不是 call graph、data flow、control flow 或 type graph。
Code Quality Governance 可用 对 DevWiki、surface、capability、symbol、graph edge、context item 记录反馈和规则。 当前主要是 read-time overlay 和治理计划，不自动修改代码。
Agent Context Pack 可用 为开发任务生成相关能力、文件、符号、风险、测试建议和证据。 上下文包不是自动开发结果，仍需 Coding Agent 验证。

自我评估：是否存在偏差或虚假认知

判断点 评估 原因 防护方式
“项目能审计本项目代码” 基本成立 已有真实仓库 E2E 测试覆盖 DevWiki、Graph、Quality、Context。 继续要求 evidence、line range、artifact hash gate。
“项目能完整理解代码行为” 不成立 当前不做 full call graph、data flow、control flow、runtime trace、type inference。 报告和 UI 必须明确这些是非目标。
“自审结论完全客观” 有风险 自审工具和被审对象是同一个项目，可能共享盲区。 需要外部审计、人工抽样、与 Codex 终端直接读文件结果对比。
“Quality Governance 会修复问题” 需限定 当前是 feedback、rule、review、plan 和 read-time overlay，不直接改代码。 把治理结果作为审计输入，不当作自动修复完成。
“HTML 页面本身是审计证据” 需限定 HTML 是展示层，不是事实源。 事实源仍是 tests、artifacts、source files、API/MCP/CLI outputs。

  • 代码是否不存在安全漏洞？
  • LLM 总结是否无需人工审计即可发布？

最终审计意见

当前项目已经具备“对本项目做结构化代码资产审计”的核心能力，并且可以把结果通过 HTML、DevWiki、Graph、 Quality Plan 和 Agent Context Pack 呈现给人类或 Agent。

但更稳妥的表述是：它是一个 evidence-backed project intelligence baseline， 不是完整程序分析器，也不是能独立判定所有代码正确性的审计系统。 后续如果要把它升级成更强的自动审计平台，应补 LSP/AST 深化、跨语言索引、调用图、影响分析、 大仓库性能基线和外部审计对照集。
