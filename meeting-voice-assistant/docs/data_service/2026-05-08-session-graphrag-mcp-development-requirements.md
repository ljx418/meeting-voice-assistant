# Session GraphRAG MCP Development Requirements

Date: 2026-05-08

Owner repo for implementation: `~/Desktop/workspace/data_service`

Consumer repo for first integration: `~/Desktop/workspace/meeting-voice-assistant`

Implementation update: the Data Service MCP MVP now exposes the session tools
listed in this document. The current meeting application integration uses those
tools through `app.core.data_service_mcp_client` and treats failures as
degraded knowledge graph state, not as upload/transcription failures.

## Background

The meeting application has migrated knowledge persistence, GraphRAG, LLMWiki,
source trace, and cross-source retrieval responsibilities to the standalone
Data Service. The meeting backend currently keeps only compatibility boundaries
and does not import `data_service` internals or read/write its workspace files.

The current Data Service MCP surface can import text sources, build a workspace,
query knowledge, and archive a workspace. This is enough to treat a meeting
transcript as a normal source, but it does not yet provide a stable contract for:

- domain session IDs such as `meeting_id`
- speaker-aware or actor-aware distilled units
- relationships between actors, statements, topics, decisions, tasks, risks, and
  evidence
- session-scoped GraphRAG snapshots and community summaries
- ephemeral session lifecycle and cleanup
- MCP graph snapshot / graph neighbor APIs suitable for UI and agent consumers

This document defines the required Data Service development work. The design
must be implemented as MCP capabilities first. HTTP or CLI wrappers may exist,
but they must call the same service-layer contracts and must not become the
primary integration path.

## Design Direction

Do not implement these capabilities as meeting-only APIs. Meeting is the first
business scenario, but Data Service should expose a generic session-oriented
knowledge and graph contract that can later support interviews, calls, support
tickets, research notes, sales discovery, incident reviews, and other temporal
or conversation-like business records.

Use these generic concepts:

- `workspace`: long-lived knowledge container.
- `session`: temporary or bounded business context inside a workspace.
- `source`: imported raw material, such as transcript, markdown, PDF, note, or
  local file.
- `actor`: speaker, author, participant, system, assignee, customer, or other
  business role.
- `unit`: typed extracted knowledge unit, such as statement, question,
  decision, task, risk, issue, requirement, fact, evidence, or summary.
- `relation`: explicit graph edge between actors, units, topics, entities,
  source spans, and external knowledge snippets.
- `community`: GraphRAG cluster and summary generated for a workspace or a
  session view.
- `scope`: query/build boundary. Required values: `workspace`, `session`.

Meeting-specific naming such as `meeting_id`, `speaker`, and
`meeting_transcript` should be accepted as metadata aliases, then normalized
internally to the generic session/actor model.

## Required MCP Capabilities

### 1. Session Lifecycle

Add MCP tools for creating, inspecting, and disposing scoped sessions:

- `knowledge_session_create`
- `knowledge_session_get`
- `knowledge_session_list`
- `knowledge_session_close`
- `knowledge_session_delete`

Minimum input fields:

```json
{
  "workspace": "default",
  "external_id": "meeting-2026-05-08-001",
  "session_type": "meeting",
  "title": "项目发布计划会议",
  "ephemeral": true,
  "ttl_seconds": 86400,
  "metadata": {
    "meeting_id": "meeting-2026-05-08-001"
  }
}
```

Minimum behavior:

- `external_id` must be stable and idempotent within a workspace.
- `session_id` must be returned and used by subsequent tools.
- `knowledge_session_close` marks the session inactive and prevents accidental
  further writes unless an explicit `reopen` or `allow_closed_write` option is
  provided.
- `knowledge_session_delete` must physically remove session-scoped graph state,
  session-only sources generated by the session, communities, summaries, and
  derived caches. It must not delete unrelated workspace-global sources.
- Ephemeral sessions must support TTL cleanup through a service job and through
  explicit MCP deletion.

### 2. Generic Structured Source Ingestion

Add a generic MCP ingestion tool that accepts structured records, not only raw
text:

- `knowledge_session_ingest`

Minimum input fields:

```json
{
  "workspace": "default",
  "session_id": "ksess_...",
  "source_type": "transcript",
  "content_format": "turns",
  "title": "项目发布计划会议转写",
  "records": [
    {
      "record_id": "turn-0001",
      "actor_id": "speaker_0",
      "actor_label": "张三",
      "role": "speaker",
      "start_time": 12.4,
      "end_time": 18.9,
      "text": "我们下周一完成最终验收。",
      "metadata": {}
    }
  ],
  "metadata": {
    "meeting_id": "meeting-2026-05-08-001",
    "language": "zh"
  }
}
```

Minimum behavior:

- Support `content_format` values `text`, `markdown`, `turns`, and `json`.
- Preserve actor, timestamp, record ID, source span, and original metadata.
- Produce source trace IDs that can map graph nodes/edges back to exact input
  records or text spans.
- Allow ingestion to link against existing local files or workspace sources
  through optional `related_source_ids`, `related_paths`, or
  `auto_link: true`.
- `auto_link` must search within the selected scope and optionally the parent
  workspace, then record explicit evidence-backed links rather than only mixing
  retrieval results into text.

### 3. Session Build / Distill / Graph Materialization

Add MCP tools:

- `knowledge_session_build_start`
- `knowledge_session_build_status`
- `knowledge_session_build_cancel`

Minimum behavior:

- Build modes: `distill`, `graph`, `communities`, `full`.
- Scope must be `session` by default for session builds.
- The build pipeline must create typed units from structured source records.
- Distillation must not flatten all speaker/actor information into generic
  notes. Actor references must survive into graph materialization.

Required generic unit types:

- `statement`
- `question`
- `decision`
- `task`
- `risk`
- `issue`
- `requirement`
- `fact`
- `evidence`
- `summary`
- `topic`
- `entity`

Each unit should contain:

```json
{
  "unit_id": "unit_...",
  "unit_type": "decision",
  "text": "下周一完成最终验收",
  "actors": [{"actor_id": "speaker_0", "role": "proposer"}],
  "source_refs": [{"source_id": "src_...", "record_id": "turn-0001"}],
  "topics": ["发布计划", "验收"],
  "entities": ["项目发布", "最终验收"],
  "confidence": 0.82,
  "metadata": {}
}
```

Required relation types:

- `actor_made_statement`
- `actor_asked_question`
- `actor_proposed_decision`
- `actor_accepted_task`
- `actor_raised_risk`
- `unit_about_topic`
- `unit_mentions_entity`
- `unit_supported_by_evidence`
- `unit_related_to_source`
- `source_related_to_source`
- `topic_related_to_topic`
- `entity_co_occurs`

The relation model should remain extensible: relation types must be data-driven
or registry-based, not hard-coded only for meetings.

### 4. Session GraphRAG Query and Snapshot

Add MCP tools/resources:

- `knowledge_graph_snapshot`
- `knowledge_graph_neighbors`
- `knowledge_community_summary`
- `knowledge_session_query`

Minimum graph snapshot input:

```json
{
  "workspace": "default",
  "scope": "session",
  "session_id": "ksess_...",
  "max_nodes": 200,
  "include_communities": true,
  "include_source_refs": true,
  "node_types": ["actor", "topic", "unit", "entity", "source"]
}
```

Minimum graph snapshot output:

```json
{
  "workspace": "default",
  "scope": "session",
  "session_id": "ksess_...",
  "nodes": [
    {
      "id": "actor:speaker_0",
      "type": "actor",
      "label": "张三",
      "metadata": {"role": "speaker"}
    }
  ],
  "edges": [
    {
      "id": "edge_...",
      "source": "actor:speaker_0",
      "target": "unit:unit_...",
      "type": "actor_proposed_decision",
      "weight": 0.91,
      "source_refs": [{"source_id": "src_...", "record_id": "turn-0001"}]
    }
  ],
  "communities": [
    {
      "id": "comm_...",
      "title": "发布验收安排",
      "summary": "本社区聚合最终验收时间、测试完成和发布材料准备等内容。",
      "node_ids": ["actor:speaker_0", "unit:unit_..."]
    }
  ]
}
```

Minimum behavior:

- `scope=session` returns only the selected session graph and its session
  communities.
- `scope=workspace` returns workspace-global graph behavior.
- Session communities must be independent across sessions even when they belong
  to the same workspace.
- Deleting or closing an ephemeral session must remove or hide session community
  summaries according to lifecycle policy.
- `knowledge_session_query` must accept `scope=session` and use only the
  selected session graph unless explicitly passed `include_workspace_context`.
- Query results must include source trace and relation evidence where possible.

### 5. Actor Summary API

Add MCP tool:

- `knowledge_actor_summary`

Minimum input:

```json
{
  "workspace": "default",
  "scope": "session",
  "session_id": "ksess_...",
  "actor_id": "speaker_0",
  "include_units": true,
  "unit_types": ["statement", "decision", "task", "risk", "question"]
}
```

Minimum output:

```json
{
  "actor": {"actor_id": "speaker_0", "label": "张三"},
  "summary": "张三主要提出最终验收时间，并负责推进测试完成。",
  "topics": ["发布计划", "验收"],
  "decisions": [],
  "tasks": [],
  "risks": [],
  "questions": [],
  "source_refs": []
}
```

This tool must be generic. For meetings it is used as speaker summary; for
other domains it can summarize customer, agent, assignee, author, reviewer, or
system actors.

## Meeting Scenario Acceptance Requirements

The meeting application will use the generic MCP contract as follows:

1. Create or reuse a workspace for meeting knowledge. The default policy is one
   meeting session inside a meeting workspace, not one permanent workspace per
   meeting.
2. Call `knowledge_session_create` with:
   - `external_id = meeting_id`
   - `session_type = meeting`
   - `ephemeral = true` unless the caller explicitly wants retention
3. Call `knowledge_session_ingest` with ASR speaker turns. Each turn must
   include speaker/actor ID, optional display label, start/end time, text, and
   original metadata.
4. Call `knowledge_session_build_start(mode="full")`.
5. Poll `knowledge_session_build_status`.
6. Use `knowledge_graph_snapshot(scope="session")` to render the meeting graph.
7. Use `knowledge_actor_summary(scope="session")` to render each speaker's
   summary, topics, statements, decisions, tasks, risks, and questions.
8. Use `knowledge_session_query(scope="session")` for meeting-only Q&A.
9. On UI exit or explicit meeting close, call `knowledge_session_close`, then
   call `knowledge_session_delete` when the graph should no longer exist.

Acceptance criteria:

- Given one ASR transcript with at least three speakers and ten turns, the Data
  Service creates one session, one source, actor nodes for each speaker, typed
  units, and actor-to-unit relations.
- The graph snapshot shows separate nodes for actors, topics, units, sources,
  and entities. Speaker names must not appear only as generic entities.
- Community summaries are generated per session. Two meetings in the same
  workspace must produce different session community sets.
- Querying meeting A with `scope=session` must not return meeting B's session
  graph content unless `include_workspace_context` is explicitly enabled.
- `knowledge_actor_summary` for a speaker returns only that speaker's relevant
  statements/tasks/decisions/questions/risks with source refs.
- After `knowledge_session_delete`, `knowledge_graph_snapshot` for that session
  returns a not-found or disposed-session response, and the session graph is no
  longer available.
- Existing workspace-level ingestion/build/query behavior remains backward
  compatible.

## Integration Boundary For Meeting App

The meeting app must remain a consumer of Data Service. Do not add imports from
`data_service` internals into `meeting-voice-assistant`.

Expected client-side/server-side integration surface:

- MCP stdio is the primary contract for agent workflows.
- Optional HTTP proxy compatibility may remain under `/api/v1/knowledge/*`, but
  it should map to the same Data Service service-layer operations.
- Meeting app should send structured turns rather than only markdown whenever
  the new MCP tools are available.
- Existing markdown handoff can remain as fallback only.

Relevant current meeting app files for context:

- `backend/app/meeting_mcp/mcp_stdio.py`
- `backend/app/meeting_mcp/service.py`
- `backend/app/api/v1/data_service.py`
- `backend/app/api/v1/voice_session.py`
- `backend/app/storage/knowledge_base.py`
- `frontend/src/pages/MeetingPage.vue`

## Compatibility Requirements

- Keep current MCP tools such as `knowledge_source_import`,
  `knowledge_workspace_create`, `knowledge_build_start`, `knowledge_query`, and
  workspace archive behavior working.
- New session tools may be layered on existing workspace storage, but callers
  must not need to know the internal directory layout.
- The Data Service must not require one physical workspace per meeting to get
  session isolation.
- If a temporary physical workspace is used internally, it must be hidden behind
  the session contract and cleaned up by session lifecycle tools.
- MCP errors must be structured and actionable, including `code`, `message`,
  `retryable`, and relevant IDs.
- Build status must expose enough progress detail for UI polling:
  `queued`, `running`, `succeeded`, `failed`, `cancelled`, `disposed`.

## Suggested Implementation Phases

Phase 1: Contract and storage foundation

- Add session registry with stable `external_id`.
- Add generic structured ingestion preserving actors and source spans.
- Add session lifecycle MCP tools.
- Add unit tests for idempotent create, ingest, close, delete, and TTL metadata.

Phase 2: Speaker/actor-aware distill and materialization

- Extend distill units with actors, unit types, source refs, topics, entities,
  and confidence.
- Extend graph materializer to create actor/unit/topic/entity/source nodes and
  explicit relation edges.
- Add tests using a multi-speaker transcript fixture.

Phase 3: Session GraphRAG APIs

- Add session graph snapshot, neighbors, community summary, actor summary, and
  scoped session query.
- Ensure session community summaries do not bleed across sessions.
- Add deletion/disposal tests that verify graph state disappears.

Phase 4: Meeting app adapter and acceptance

- Add a small adapter in the meeting app that converts ASR output into
  `knowledge_session_ingest` records.
- Return `knowledge_session`, `session_graph`, and `speaker_summaries` from the
  upload session result endpoint.
- Close/delete the Data Service session graph from the meeting app when the
  upload session exits or is removed.
- Validate end-to-end MCP flow with a local meeting transcript.
- Keep markdown source import as fallback for older Data Service versions.

## Non-Goals

- Do not move ASR or meeting transcription into Data Service.
- Do not make Data Service depend on meeting app modules.
- Do not expose internal GraphRAG database paths as a public contract.
- Do not hard-code all unit or relation types as meeting-only enums.
- Do not rely on archive-only behavior for ephemeral session cleanup.
